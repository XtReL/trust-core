## Вопрос 1. Изменён один пробел в одной записи журнала

Записи пишутся `json.Marshal` без пробелов между токенами, поэтому
«изменение одного пробела» моделируется вставкой одного незначащего для JSON
пробела (вариант A — после первого `:` в записи 1, вариант B — в конце
файла записи 1). Подпись DSSE от этого не ломается (подписан base64-payload),
но меняется хэш листа RFC 6962, а значит и корень.

Ожидание: **обнаружит**. Код выхода **1**.
stdout: строки `log:`, `size:`, `root:` (без строки `OK:`).
stderr ровно:

```
 - entries on disk do not match the signed checkpoint root (log was modified)
VERIFICATION FAILED: 1 problem(s)
```

Проблема ровно одна: сама запись остаётся валидным DSSE с верной подписью,
поэтому ошибки по записи (`entry N: ...`) не будет.
Контроль: до порчи тот же verify даёт код 0 и `OK:`.

## Вопрос 2. Журнал переписан, чекпоинт переподписан тем же ключом

Модель: журнал из 3 записей, чекпоинт сохранён у клиента. Оператор
заменяет запись 0 другой (валидно подписанной тем же аттестатором)
аттестацией и пересобирает журнал тем же ключом оператора, размер снова 3.

- Без `-previous`: **не обнаружит**, код 0, `OK:` (так и заявлено в README,
  «Модель безопасности»).
- С `-previous <сохранённый чекпоинт>`: **обнаружит**, код **1**, stderr:

  ```
   - history was rewritten: first entries no longer match the previous checkpoint
  VERIFICATION FAILED: 1 problem(s)
  ```

- С `-previous <пустой файл>`: в `cmdVerify` файл читается в
  `opts.Previous`, а `verify.Log` проверяет историю только при
  `len(opts.Previous) > 0`. Пустой файл => проверка **молча пропускается**:
  код **0**, `OK: ...`, строки `history:` нет, ни ошибки, ни предупреждения.
  Переписанная история при этом проходит. Это fail-open: клиент, у которого
  файл сохранённого чекпоинта оказался пустым (обрезан, не дописан), считает,
  что история проверена. Ожидаю это как дефект.
- Дополнительно: `-previous` на несуществующий файл — код 2,
  `error: open ...: no such file or directory`.

## Вопрос 3. Несуществующие пути в -log и -log-pub

- `-log` указывает на несуществующий каталог: ключи читаются успешно, затем
  `verify.Log` возвращает ошибку чтения `checkpoint`, а `cmdVerify` вызывает
  `fail(...)`. Код **1**, stderr:
  `VERIFICATION FAILED: open <dir>/checkpoint: no such file or directory`.
- `-log-pub` указывает на несуществующий файл: `keys.LoadPublic` возвращает
  ошибку, она уходит в `main`. Код **2**, stderr:
  `error: open <path>: no such file or directory`.
- Сравнение с README.md (строка «Коды выхода: `0` — всё проверено, `1` —
  проверка не прошла, `2` — ошибка использования»):
  - `-log-pub` => 2 согласуется с README, если считать отсутствующий
    файл ключа ошибкой использования.
  - `-log` => 1 **не согласуется**: это та же категория ошибки (путь из
    аргумента не существует, I/O), но сообщается как «VERIFICATION FAILED»,
    то есть как провал проверки журнала. Комментарий в шапке
    `cmd/trustcore/main.go` прямо говорит «2 = usage or I/O error», так что
    код расходится и с собственной документацией CLI. README при этом
    вообще не упоминает I/O-ошибки, т.е. неполон.
  Итог ожидания: два одинаковых по природе случая дают разные коды (1 и 2);
  с README совпадает только случай `-log-pub`.
