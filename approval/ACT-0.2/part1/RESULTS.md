# ACT-0.2, часть 1 — результаты независимых контролей

Объект: XtReL/trust-core @ f419b0d1693e6d3c06b7effa813239d129f31d6d
(совпадает с `main` на момент проверки). Go 1.24.7 linux/amd64, `GOTOOLCHAIN=local`.
Ожидания записаны в `EXPECTED.md` и закоммичены (ceb2616) до первого прогона.

Как воспроизвести (из клона репозитория): `bash approval/ACT-0.2/part1/run_part1.sh`.
Скрипт распаковывает объект через `git archive` во временный каталог, каждый
контроль создаёт свои ключи и журналы в отдельном `mktemp -d` и удаляет его
на выходе. Полный вывод каждого прогона — `out/<контроль>.out`. Контроль
завершается с кодом 1, если хоть одно утверждение расходится с ожиданием.

| Контроль | Файл вывода | Код | Утверждения |
|---|---|---|---|
| `q1_whitespace.sh` | `out/q1_whitespace.out` | 0 | 14/14 совпали |
| `q2_rewrite.sh` | `out/q2_rewrite.out` | 0 | 18/18 совпали |
| `q3_exit_codes.sh` | `out/q3_exit_codes.out` | 0 | 13/13 совпали |

Расхождений между ожиданиями и фактом нет.

## 1. Один пробел в одной записи

**Ответ: обнаруживает.** Код выхода **1**. stdout — строки `log:`, `size:`,
`root:` без `OK:`; stderr:

```
 - entries on disk do not match the signed checkpoint root (log was modified)
VERIFICATION FAILED: 1 problem(s)
```

Уточнение по модели: записи пишутся `json.Marshal` в компактной форме и
не содержат ни одного байта пробела (контроль это фиксирует: «entry 1 has 0
space byte(s)»). Поэтому «изменение одного пробела» проверено как добавление
одного незначащего для JSON пробела: (A) после первого `:`, (B) в конце
файла. В обоих вариантах запись остаётся валидным JSON и валидным DSSE
(подпись покрывает только payload), поэтому ошибки по самой записи нет, а
расхождение ловится только по корню Меркла — ровно одна проблема. Заявление
README («Изменение даже одного пробела обнаруживается») подтверждено.

## 2. Переписанная история, чекпоинт переподписан тем же ключом

Модель: журнал из 3 записей; клиент сохранил чекпоинт; оператор
пересобрал журнал тем же ключом журнала, заменив запись 0 другой
аттестацией (подписана тем же аттестатором), записи 1–2 те же, размер 3.

- Без `-previous`: **не обнаруживает**, код 0, `OK:`. Это заявленное
  ограничение (README, «Модель безопасности»).
- С `-previous <чекпоинт до переписывания>`: **обнаруживает**, код **1**:

  ```
   - history was rewritten: first entries no longer match the previous checkpoint
  VERIFICATION FAILED: 1 problem(s)
  ```

- С `-previous <пустой файл>`: **проверка истории молча пропускается.**
  Код **0**, печатается `OK: checkpoint signature, Merkle root and all entry
  signatures verified`, строки `history:` нет, stderr пуст; в `-json` нет
  `previousSize`, `"ok": true`. Переписанный журнал проходит.
  Причина: `verify/verify.go:93` — `if len(opts.Previous) > 0 { ... }`;
  `cmd/trustcore/main.go:215-219` читает файл и не проверяет, что он не пуст.
  **Оценка: дефект (fail-open).** Клиент явно запросил проверку истории, а
  получил «OK» без неё; признаком служит лишь отсутствие строки `history:`.
  Пустой файл — реалистичный случай (обрезанная запись, неудачное
  копирование, `> file` в скрипте).
- Дополнительно: `-previous` на несуществующий файл — код 2,
  `error: open ...: no such file or directory` (fail-closed).

## 3. Коды выхода при несуществующих путях

| Случай | Код | stderr |
|---|---|---|
| каталог `-log` не существует | **1** | `VERIFICATION FAILED: open <dir>/checkpoint: no such file or directory` |
| файл `-log-pub` не существует | **2** | `error: open <path>: no such file or directory` |
| оба не существуют | 2 | ключ читается первым |
| не задан обязательный `-log-pub` (справочно) | 2 | `error: verify: -log-pub is required` |

Сравнение с README.md:45 — «`0` — всё проверено, `1` — проверка не прошла,
`2` — ошибка использования»:

- `-log-pub` → 2: согласуется, если считать несуществующий файл ключа
  ошибкой использования.
- `-log` → 1: **не согласуется.** Несуществующий путь из аргумента —
  та же ошибка использования / ввода-вывода, что и для `-log-pub`, но она
  выдаётся как «VERIFICATION FAILED» с кодом 1, то есть неотличима для
  вызывающей стороны (CI) от обнаруженной подмены. Это расходится и с
  шапкой `cmd/trustcore/main.go:4` («2 = usage or I/O error»). Причина:
  `verify.Log` возвращает ошибку чтения чекпоинта, а `cmdVerify`
  (`main.go:220-223`) любую ошибку `verify.Log` отдаёт в `fail()`.
- README неполон: про I/O-ошибки не говорит вовсе, тогда как код CLI
  отдельно их классифицирует.

**Ответ: нет, не совпадает полностью** — однотипные ошибки дают разные
коды (1 и 2), и случай `-log` противоречит документированной классификации.

## Замечания о ходе работы

- Первые два прогона `run_part1.sh` упали из-за ошибок в самом контроле, а
  не в объекте: (1) `git archive` запускался из подкаталога и упаковывал
  только его — исправлено на корень репозитория; (2) необъявленный `$3` в
  `lib.sh` при `set -u`. Эти выводы перезаписаны финальным прогоном.
- Код объекта не изменялся; все прогоны — в копиях `git archive`.
- Ключи создавались только во временных каталогах и удалены вместе с ними
  (строка `cleanup:` в конце каждого вывода).
