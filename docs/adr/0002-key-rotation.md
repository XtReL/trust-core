# ADR 0002. Ротация ключа журнала: эпохи, связанные записью-генезисом

Статус: **принято** (с поправками по итогам двух ревью). Место: `trust-core/docs/adr/0002-key-rotation.md`; в `devsecops-gatekeeper` — ссылка из ADR 0001.

## Контекст

В ADR 0001 записано «ротация — добавлением нового ключа, верификатор принимает несколько». **Для текущего кода это неверно:**
- `filelog.Open` проверяет текущий чекпоинт ключом, которым будет подписан следующий;
- `verify.Log` принимает один ключ журнала.

Смена ключа ломает запись в журнал; потеря устройства с ключом не даёт продолжить журнал; компрометацию нельзя ограничить.

## Решение: эпохи

Отвергнуты:
- **A** — ротация внутри журнала: проверка с состоянием в критичном коде, расхождение с практикой CT и Tessera;
- **C** — просто список доверенных ключей: скомпрометированный ключ остаётся действующим навсегда.

### 1. Эпоха = журнал с одним ключом
- Эпоха 1 — существующий журнал **без изменений**: origin `github.com/XtReL/devsecops-gatekeeper/gatekeeper-evidence/v1`, ветка `gatekeeper-evidence`.
- Эпоха k ≥ 2: origin `<origin эпохи 1>/e<k>`, ветка `gatekeeper-evidence-e<k>`, формат `filelog` тот же.
- Эпохи образуют **линейную цепочку**. Два генезиса, ссылающихся на одну и ту же предыдущую эпоху, — это развилка, сигнал тревоги.

### 2. Два вида ротации (не три)
- **`planned`** — владелец старого ключа участвует: генезис подписан **и старым, и новым** ключом.
- **`unplanned`** — старого ключа нет. **Потеря и компрометация криптографически неотличимы:** если ключа нет у вас, нельзя доказать, что его нет у кого-то ещё. Генезис подписан только новым ключом; принимается **только по явному решению проверяющего**.

### 3. Запись-генезис — запись 0 каждой эпохи k ≥ 2
Обычный in-toto Statement v1 в DSSE; форматы не меняются.
- `predicateType`: `https://github.com/XtReL/trust-core/log-genesis/v1`.
- Субъект: `name` = origin предыдущей эпохи, `digest.sha256` = hex финального корня предыдущей эпохи.
- Предикат:
  - `epoch` — номер новой эпохи;
  - `predecessorOrigin`, `predecessorSize`, `predecessorRoot` (base64, как в чекпоинте);
  - `predecessorCheckpoint` — **точный текст** подписанного чекпоинта C2SP (signed-note, байты файла `checkpoint`);
  - `predecessorKeyID`, `newKeyID`;
  - `rotation`: `planned` | `unplanned`;
  - `note` — необязательный свободный текст, на проверку не влияет.
- Подписи DSSE: новый ключ — всегда; старый — при `planned`.

### 4. `keyid`
Нижний регистр, hex, SHA-256 от **сырых 32 байт** публичного ключа Ed25519 (как `keys.KeyID` в v0.1.0). Хэш ключа из формата C2SP signed-note (4 байта) — другое значение, и для `keyid` он не используется.

### 5. Точка заморозки
- Предыдущая эпоха считается закрытой на `predecessorCheckpoint`. Для неё **авторитетным считается этот чекпоинт**, а не текущий файл `checkpoint`.
- Записи после точки заморозки — «**не подтверждены**»: проверка их явно перечисляет, но доверия им не даёт.
- При `planned` рост старой эпохи после заморозки — **ошибка** (признак злоупотребления старым ключом).
- При `unplanned` точка заморозки задаётся **внешним доверенным чекпоинтом** (копия у владельца или аудитора), а не текущим состоянием файлов: им мог управлять злоумышленник. Префикс старой эпохи обязан совпасть с этим чекпоинтом, иначе история была переписана до заморозки, и ротация отклоняется.

### 6. Записи-преемника нет
Запись `log-successor` в старой эпохе **не используется**. Доказательство плановой ротации — двойная подпись генезиса. Старая эпоха просто обрывается и не меняется при ротации. Это убирает запись в два журнала за одну операцию и возможность подделать «преемника» скомпрометированным ключом.

### 7. Проверка цепочки по манифесту
`verify.Chain` и CLI `trustcore verify-chain -manifest FILE`. Манифест хранит **проверяющий** у себя, это его доверенный слепок:

```json
{
  "base": "github.com/XtReL/devsecops-gatekeeper/gatekeeper-evidence/v1",
  "epochs": [
    {"epoch": 1, "log": "ev-e1", "publicKey": "keys/e1.pub", "lastKnownCheckpoint": "cp/e1"},
    {"epoch": 2, "log": "ev-e2", "publicKey": "keys/e2.pub", "acceptUnplanned": "<newKeyID>"}
  ]
}
```

Пути — относительно манифеста. Правила:
- **публичные ключи берутся только из манифеста проверяющего**, никогда из проверяемого репозитория (`.gatekeeper/keys/` — только для сверки глазами);
- каждая эпоха проверяется своим ключом, как сегодня (`verify.Log` не меняется);
- для k ≥ 2 **запись 0 обязана быть генезисом**, подписанным ключом эпохи k, с `epoch == k`, `predecessorOrigin` = origin эпохи k−1, `predecessorKeyID`/`newKeyID` = keyid ключей манифеста; `predecessorCheckpoint` проверяется ключом эпохи k−1, его размер и корень совпадают с полями предиката и субъектом, префикс эпохи k−1 совпадает с ним;
- `planned` без валидной подписи старым ключом → **ошибка** (не понижается молча до `unplanned`);
- `unplanned` без `acceptUnplanned`, равного `newKeyID`, → **ошибка**;
- `lastKnownCheckpoint` — прежний `-previous` для каждой эпохи: защищает от отката всей цепочки к более ранней истории.

## Обратная совместимость
- Существующий журнал = эпоха 1; `verify.Log`, `trustcore verify` и формат на диске не меняются.
- Тест с фикстурой журнала формата v0.1.0 (коммитятся только журнал и публичный ключ) проверяется новой версией.
- Все изменения аддитивные.

## Ограничения (честно)
- Ротация защищает **будущее**. Прошлое при компрометации защищают только копии чекпоинтов у других сторон (аудитор, на этапе 6 — свидетель).
- Точка заморозки не решает **показ разной истории разным сторонам** (split view). Это задача свидетелей и сверки чекпоинтов между проверяющими, а не ротации.

## Процедура (runbook — в Gatekeeper)
1. Новый ключ — на устройстве владельца.
2. `trustcore rotate`:
   - `planned`: с обоими ключами, точка заморозки — текущее проверенное состояние;
   - `unplanned`: без старого ключа, с обязательным доверенным чекпоинтом.
3. Push ветки `gatekeeper-evidence-e<k>`.
4. `gh secret set GATEKEEPER_SIGNING_KEY` из stdin: секрет с тем же именем **перезаписывается**, старого значения в CI не остаётся. После `planned` старый приватный ключ на устройстве уничтожить.
5. PR: `.gatekeeper/evidence.json` (эпоха, ветка, origin) и `.gatekeeper/keys/e<k>.pub`.
6. **При `unplanned`:** уведомить проверяющих вне журнала — новый origin, новый keyid, причина, дата; для публичного репозитория — ещё и GitHub Security Advisory. Проверяющий сверяет keyid с владельцем лично и только потом ставит `acceptUnplanned`.
7. Ruleset `evidence-protection`: две явные цели — `gatekeeper-evidence` и `gatekeeper-evidence-e*` (не широкий шаблон).
8. Этап 6: свидетели перестают соподписывать старую эпоху после заморозки и перенастраиваются на новый origin и ключ.

**Учения:** самотест CI (обе ротации на bare-репозиториях) и один ручной прогон на тестовом репозитории. Боевой журнал на новую эпоху не переводится без реальной причины.

## Отвергнутые предложения ревью
- **Дублировать данные предшественника в `.gatekeeper/evidence.json`:** единственный источник истины — генезис; дубли расходятся.
- **Дополнительные причины (`retired`, `policy`):** не меняют проверку; для пояснения есть `note`.
- **`log-successor` с запретом доверять ему при компрометации:** снимается удалением записи-преемника (п. 6).
