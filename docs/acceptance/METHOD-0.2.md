# Методика приёмки работы ИИ-агентов и подрядчиков, версия 0.2

Статус: черновик. Версия считается зафиксированной, когда этот файл закоммичен. Акт ссылается на версию и на sha256 файла.

## 0. Назначение и границы

Приёмка отвечает на вопрос, можно ли опираться на сданное и что делать дальше. Это независимая проверка по доказательствам. Приёмка ничего не чинит, не сертифицирует и не гарантирует.

Продукт приёмки это акт. Акт является протоколом проверки на дату, на коммит и по версии методики. Слова «сертификат» и «гарантия» в акте не используются.

## 1. Ядро (без изменений с 0.1)

1. Каждое заявление попадает в одну из колонок: заявлено, проверено, не проверено и почему.
2. Проверка повторяема.
3. У отрицательного результата есть положительный контроль.
4. Вывод не шире проверки.
5. У акта есть версия методики.
6. Зафиксированные акты не переписываются.

Каркас взят из метрологии. Проверки берутся из готовых стандартов (ISO/IEC 25010, OWASP ASVS, OWASP Top 10 для LLM, CWE, SLSA). Собственный каталог методики описывает только ошибки работы агентов.

## 2. Термины

- Заявление. Утверждение из материалов репозитория о том, что система делает или чем является, с путём и строкой.
- Проверка. Действие, которое даёт результат по заявлению.
- Контроль. Проверка самой проверки, то есть подложенный образец или намеренная поломка, которую проверка обязана обнаружить.
- Способ. Чем получен результат: прогон, текст, чтение, наблюдение (раздел 5).
- Фиксация. Push акта в удалённую ветку. С этого момента акт не меняется.
- Ревизия. Отдельный документ с поправками к зафиксированному акту или к предыдущей ревизии.

## 3. Объём и материалы

1. Код во время приёмки не исправляется. Исправления делаются в отдельной ветке от основной, после них проводится новая приёмка или ревизия на новый коммит.
2. Секреты не выводятся. Литералы, похожие на секреты, указываются только как путь:строка, длина и энтропия. Ключи для контролей создаются на месте и удаляются вместе с временными каталогами.
3. Положительные контроли и мутации выполняются во временных копиях. Если копия сделана через `git archive`, в слепые зоны записывается, что в ней нет истории и нет файлов с `export-ignore`.

## 4. Отбор заявлений

1. Источники задаются в задании, по умолчанию README и docs. Заявление записывается цитатой с путём и строкой.
2. Лимит задаётся в задании, по умолчанию 15.
3. Порядок отбора по цене пропуска, от высокой к низкой.
4. Заявления, не вошедшие в лимит, перечисляются списком. Без этого счёт «N из M» не отражает охват.
5. Собственные наблюдения проверяющего записываются в раздел «Находки вне заявлений» и в счёт не входят. Проверяющий не формулирует заявления за репозиторий.

## 5. Статусы и способы

Статусы: П (подтверждено), О (опровергнуто), Н (не определено, с причиной).

Способы:

- Прогон. Запуск кода, теста или контроля.
- Текст. Поиск, подсчёт или сравнение по файлам, когда заявление касается самих файлов (версия в go.mod, длина описания, закрепление по SHA).
- Чтение. Вывод о поведении из чтения кода без запуска.
- Наблюдение. Факт, сообщённый владельцем (настройки сервисов, состояние развёртывания), с датой.

Правила:

1. У каждого П и О указан способ.
2. Если строка проверена двумя способами, способом считается тот, который дал результат. Второй указывается в примечании.
3. Итог акта пишется раздельно по способам.
4. Для заявлений о поведении способ «чтение» допустим, но такой результат слабее прогона, и это видно в итоге.

## 6. Контроли

1. Любой результат «0 найдено» или «нет» записывается в одной строке с контролем: что подложено и что та же команда это нашла.
2. Контроль должен уметь упасть. Ожидаемый результат проверяется внутри контроля (t.Fatalf, exit 1), запись в лог проверкой не считается. Контроль, который не может упасть, контролем не является.
3. Для опровергнутого заявления контроль утверждает наблюдаемый дефект. После исправления кода такой контроль краснеет и требует пересмотра статуса.
4. Для заявлений высокой цены, подтверждённых прогоном, проверяется способность контроля краснеть: во временной копии код намеренно ломается, и контроль обязан упасть. Число мутаций и число обнаруженных указывается в акте.
5. Контроли сохраняются файлами сразу, в `docs/acceptance/controls/<номер акта>/`. Файлы Go хранятся с окончанием `.txt`, чтобы сборка и линтеры их не трогали. В README папки для каждого контроля указаны номер заявления, куда положить файл во временной копии, команда и ожидаемый результат.
6. Если контроль восстановлен по памяти сессии, а не сохранён файлом, это указывается: восстановленный контроль не является побайтной копией запущенного.
7. Если контроль краснел и решено, что ошибка в контроле, а не в коде, в акте указывается, что было красным, почему виноват контроль и что изменено. Это решение относится к классу 3 каталога и должно быть проверяемым.

## 7. Эталоны

1. Эталонные значения (тестовые векторы, контрольные суммы, ожидаемые выводы) берутся из внешнего источника с адресом и версией: файл стандарта, тесты эталонной реализации, опубликованный релиз.
2. Память модели эталоном не является, это заявление. Совпадение значения из памяти с результатом кода ничего не доказывает.
3. Если источника нет, статус заявления, которое держится на эталоне, понижается до Н с причиной «эталон без источника».

## 8. Чтение и доказательства

1. Вывод по чтению записывается вместе с допущениями. Пример: «перед API нет доверенного прокси, выставляющего заголовок».
2. Документ репозитория может быть только источником заявления. Доказательством для другого заявления того же репозитория он служить не может.
3. Числа приводятся с определением. Если написано «изменилось N файлов», перечисляется набор путей, по которому считали.
4. Даты точные. Округления из интерфейсов («4 месяца назад») переводятся в дату.

## 9. Окружение и сеть

1. По умолчанию сеть закрыта. Разрешается загрузка зависимостей по lock-файлам в режиме только чтения (для Go `GOFLAGS=-mod=readonly`). Если lock-файлы требуют изменений, проверяющий останавливается и спрашивает.
2. Любая автоматическая загрузка (toolchain, инструменты) записывается в шапку.
3. Если для проверки нужна сеть сверх этого, она используется только в одноразовой копии. В акт пишутся дата, что загружено и sha256 созданных файлов. Созданные файлы в репозиторий не коммитятся.
4. Если обязательная проверка репозитория (например, `check.sh`) зелёная только с сетью, она запускается в одноразовой копии, совпадающей с веткой акта. Это записывается в акт.

## 10. Шапка акта

- репозиторий и видимость (публичный или нет);
- проверяемый коммит, полный хэш;
- дата;
- версия методики и sha256 её файла;
- тип: самопроверка, внешняя приёмка, ревизия;
- окружение: toolchain, версии инструментов, автозагрузки, отступления по сети;
- проверяющий: модель и ссылка на сессию;
- авторство кода: по `Co-Authored-By` из git log и со слов владельца для коммитов без отметки;
- уровень независимости (раздел 11).

## 11. Независимость

Шкала, от слабой к сильной:

1. та же сессия, которая писала код;
2. та же модель, новая сессия без общего контекста;
3. другая модель того же семейства;
4. модель другого разработчика;
5. человек.

Правила:

1. Переключение модели внутри сессии уровень не повышает, контекст остаётся общим.
2. Соседняя версия той же линейки моделей отмечается отдельно.
3. Независимость важнее всего для результатов по чтению и для эталонов. Результат прогона с контролем, способным упасть, от проверяющего зависит меньше: его повторит любой.

## 12. Решение

1. Варианты: принять, принять с условиями, не принимать. Решение можно давать отдельно по частям системы (например, по режимам работы).
2. Обоснование решения ссылается только на строки с тем способом проверки, который в нём назван. Если написано «подтвердилось прогонами», строки по чтению в ссылку не входят.
3. Риски ранжируются по цене пропуска.
4. Слепые зоны перечисляются явно.
5. Команды для повторения даются командами или ссылками на файлы контролей. Описание словами командой не считается.

## 13. Каталог ошибок работы агентов

Классы версии 0.1, в 0.2 без изменений:

1. Утверждение шире проверки.
2. Тест проходит вхолостую.
3. Ошибка в тесте похожа на ошибку кода.
4. Противоречивые требования.
5. Документация отстала от кода.
6. Неверная конфигурация принимается молча.
7. Скрытый сбой.
8. Слепое доверие заголовкам прокси.
9. Отсутствие строки читается как ноль.

Правила:

1. Находки раскладываются по классам каталога. В «Кандидаты в каталог» попадает только то, что ни в один класс не входит.
2. Фраза «класс не выявлен» пишется только вместе с методом поиска. Если класс не искали, пишется «не искался».
3. Каталог меняется только с новой версией методики.

Кандидаты (в каталог не входят):

- Н1. Хэш без соли выдаётся за маскировку (ACT-0.1).
- Н2. Диагностика указывает не на ту причину (ACT-0.1).
- Н3. Мёртвый код безопасности (ACT-0.1).
- Н4. Запас тайм-аута меньше разброса прогона (ACT-0.1).
- Н5. Эталон из памяти модели выдан за источник (приёмка trust-core, 2026-10-10).

## 14. Фиксация и ревизии

1. Акт фиксируется push в удалённую ветку. До фиксации автор акта может его дописывать.
2. После фиксации акт не меняется. Поправки выпускаются ревизией: отдельный файл `<номер акта>-REV-<n>.md`.
3. Ревизию нельзя делать в сессии, которая составила акт. Это относится и к сверке, и к записи файла ревизии.
4. Ревизия указывает, что именно меняется, на каком основании и какой итог получается после поправок.
5. Ревизии тоже не переписываются. Поправка к ревизии выпускается следующей ревизией.
6. Если ревизия писалась по чужому заданию, в шапке указывается, кто готовил поправки и кто записал файл.

## 15. Раскрытие

1. Перед фиксацией проверяется видимость репозитория.
2. Если репозиторий публичный, а находки высокой цены касаются развёрнутой системы, акт в публичную ветку не отправляется. Решение принимает владелец.
3. Состояние развёртывания записывается фактами: дата, коды ответов, число установок. Адреса, имена приложений и служебные URL в акт не пишутся.

## 16. Изменения относительно 0.1

- Введены способы проверки и раздельный итог по способам (раздел 5).
- Контроль обязан уметь упасть, контроли сохраняются файлами сразу, для заявлений высокой цены проверяется способность контроля краснеть (раздел 6).
- Эталоны только из внешнего источника (раздел 7).
- Допущения при чтении, запрет на доказательство документами того же репозитория, определения для чисел (раздел 8).
- Правила сети и одноразовых копий (раздел 9).
- Шапка расширена: окружение, проверяющий, авторство, независимость, видимость (разделы 10 и 11).
- Обоснование решения проверяется по правилу «вывод не шире проверки» (раздел 12).
- Правила отбора заявлений и находок вне заявлений (раздел 4).
- Фиксация, ревизии и запрет ревизии в сессии автора (раздел 14).
- Правила раскрытия (раздел 15).
